# Editing reference: start here

Use `get_editing_reference` before authoring a nontrivial recipe. It is a free, read-only reference lookup, not a generation request. Topics: `overview`, `brief`, `production`, `yaml`, `media`, `transitions`, `effects`, `looks`, `motions`, `text`, `fonts`, `audio`, `jobs`, `scenes`, `scene-runtime`, `scene-authoring`, `scene-templates`, `film-styles`, `film-techniques`, `commands`, `styles`, `examples`.

Exact IDs, searches and later pages omit the repeated full guide by default; `includeGuide:true` restores it or use the separately readable `guideUri`. The unfiltered first page still includes guidance. Preflight returns compact diagnostics, requirements, plan summary, versions and reviews; use `fullResult:true` only when reading the normalized document/plan/recovery is necessary. OpenCode's optional `checkpointFile` saves these versions; `captionBaselineFile` compares all text entries and caption result IDs, while paid `checkpointFile` applies the reviewed YAML hash automatically. These are tool inputs, not YAML fields or spending consent.

For cinematic direction, prettier/cinematic animation or a specific visual language, read `film-styles`: 66 pinned style prompts with exact-ID source/provenance and an adaptation guide. `film-techniques` provides selected directing guides and pure visual-code references. These are not YAML presets or an executable local production pipeline. Use the `machinal-cinema` skill, existing Svelte/SceneThree engine and normal caption/source/spending safeguards; native `scene-templates` include Swiss grid, blueprint mechanism and paper-stage examples. Importing a reference is not model training or proof of aesthetic quality.

Prefer directly exposed native tools when available. Discover unknown MCP tools once, reuse exact signatures and read independent guides concurrently. Cache schema/capabilities until schemaHash changes. Do not use web search for MCP names or suggest_tools before every operation. Local setup installs no hosted credential/download companion; use the actual host's approved transfer tools, not an invented machinal_download capability.

MCP scenes use `topic=scene-authoring`: the current client writes Svelte, `compile_scene` validates/saves source, and example `client-scene` places the pinned asset in video tracks. `get_scene_source` supports edits. Pending scene.generate/scene.edit examples are legacy site references, not new MCP submissions. Compilation, scene frames and final encoding use the user's local hardware without machinal billing. AI images/TTS/captions may charge the user's own OpenRouter account.

## Required authoring workflow

After the brief, use topic `production`: director contract → focused pre-code critic → current-client builder → evidence-based pre-render critic. Keep the existing scene-engine. Compare the contract's subject/action, independent motion, handoffs and effect score with Svelte source and `compile_recipe.editorialReview`, which inventories actual resolved junctions/treatments without inspecting pixels. This is a quality checkpoint within approved work, not a second user plan confirmation, a server-model call or permission for paid previews.

1. Establish the brief together before authoring: read topic `brief` (`get_editing_reference(topic=brief)`). Ask about missing video type/goal, duration, destination/aspect and output resolution, visual sources/style and audio/text; wait for the user's reply. Use the host's native question tool (OpenCode: `question`) with one `questions` array, not a numbered chat questionnaire; use an unnumbered fallback only if no interactive tool exists. Recommend relevant image/scene/footage options in that form. After the user answers, summarize the agreed direction briefly and proceed immediately with the authorized work in the same turn, without a separate plan confirmation. Do not re-ask answered questions or impose a questionnaire on a complete brief or “you decide” request. Include known permissions as separate explicit questions in the same form where possible; a cancelled form is not consent. Ask before listing existing/cloud media, then use `list_media(userApproved:true, storage:s3|volume|all)` and follow `nextOffset`. Ask separately before downloading or inspecting/using named files; `request_media_access` prepares a question, never an approval. Read pinned metadata only after use consent. Read the existing recipe/project before changing it.
2. Read `get_recipe_schema` for the document shape, `get_capabilities` for the deployed catalog/commands, and topic `yaml` for the composition envelope and field semantics. Catalog data describes features, not provider readiness or permission to spend.
3. Read topic `styles`, optionally with an exact style ID. Pick an appropriate profile or derive a combination from the brief. Explain the choices: pacing; cut versus transition; one coherent look; motion; typography/captions; audio; whether a generated scene is necessary. Current user instructions override installed defaults.
4. Look up the **exact selected IDs** in `transitions`, `effects`, `looks`, `motions`, `text` or `fonts` before using them. A lookup preserves the real catalog's summaries, algorithms, parameter descriptions, defaults, bounds, integer flags, `noRamp`, look expansion and text values. Do not infer behavior from a name alone. Search is literal, case-insensitive and paginated; follow `nextOffset` to see more entries.
5. Read `scenes`/`jobs` and evaluate animated Svelte scenes alongside footage/stills when planning video beats. For narrated edits, keep beat times provisional until a separate timing-first `generate_assets` submission has completed speech and requested captions, without image/scene jobs. Read `get_job_result` once, then use actual audio duration and caption cues to finalize image holds, 2D/Three.js scene timing and placements in a second edited composition. Preserve resolved voice/captions, never regenerate them or add unrequested TTS/captions. See `narration-timing` then `narrated-documentary`; unchanged `sourceJobId` cannot add visuals. Identify useful moments from supplied copy, verified narration/cues or actually inspected sources; show timeline start/duration, message, visual choice and why motion helps. Independently moving objects, image-based layouts and changing diagrams need more than a pan/zoom over a still. Propose suitable scenes proactively, not only when the user names `scene.generate`; honor no-generation briefs and omit scenes that add no value. Scene designs are prompt directions, not scene preset IDs. See `scene-image-insert` for a full mixed-footage example.
6. Choose the closest complete example from topic `examples` and adapt it to real metadata. Example filenames, asset versions, transcripts and snapshots are synthetic fixtures, not media that exists in the user's project. Never execute a pending generation example just because it was returned.
7. Author a complete local `.edit.yaml` composition and validate, then compile only when the normalized plan is needed. Cache schema/capabilities until schemaHash changes and use targeted preset lookups. Inspect diagnostics, requirements, measured durations and overlaps. Draft/pending output is not a finished video. After generation, use get_job_result for resolved YAML or sourceJobId for unchanged continuation; do not hide errors by removing requested treatments.
8. Explain requested provider actions and uncertain OpenRouter costs; obtain explicit source-use/provider-spending authorization before `userApproved:true`. Local encoding needs no machinal balance. Reuse exact idempotency keys on uncertain retries.
9. After consent, `get_video_result(delivery:link,userApproved:true)` gives a temporary one-file volume download link. Return its exact URL/expiry and disclose same-machine reachability. No S3 or hosted credentials are used. Explicitly requested client-local downloads use `delivery:local`, `get_download_preferences` and approved `set_download_preferences`; ask when unset, never overwrite, and distinguish the client directory from Docker storage. Use `wait_for_job`, not repetitive progress lookups.

## Decision discipline

Treat existing YAML captions as read-only unless the user explicitly requests a caption change. Preserve complete entries: exact text/word spacing and line breaks, grouping, IDs/resultTextIds, timings, layout and animation/highlighting/effects. Existing caption configuration overrides style/profile/`captionMaxWords` defaults; four-word/two-line defaults apply only to NEW caption generation. Adapt visuals around captions, never reflow captions to fit scenes. Patch the resolved baseline and compare complete caption entries before submission; read topic `text` for preservation checks and encoding-only repairs.

Treat requested or AI-proposed runtime as approximate unless the user explicitly sets a hard duration cap. If a planned 30-second video produces 38–40 seconds of successful narration, keep the voice/captions and extend the video with longer/recompiled scenes or relevant additional client-authored scenes within the approved visual scope. Do not regenerate, truncate or speed up narration to match an estimate, or rerun successful captions/images. Update placements/transition overlaps to cover the measured audio end, state the adjusted runtime and proceed without reconfirmation within existing permissions. Resolve an explicit hard duration cap or spending limit before changing paid narration or exceeding approval. Read `jobs` for retiming/asset-duration details.

Image sourcing and presentation are separate decisions. A request to use/find/generate images for a video does not mean “no animated scenes”: ask once about integrating those images into Svelte scenes when undecided, with genuine Three.js where depth, geometry or spatial action adds value. Respect explicit still-only/no-generation choices and existing delegation; standalone image-search tasks stay image-search tasks. Read topic `brief` for the question and `scenes` for integrated storyboards.

For expressive/bold briefs, plan and implement an **effect score** (purpose, target, timing, exact supported preset/params), not only a grade and repeated fades. Include a subject-specific signature reveal/transformation or spatial action and intentional continuity between images, scenes and footage. Read `effects` and `styles`; their restraint/accessibility rules prevent noise, not visual ambition. Minimal briefs remain minimal. Verify the selected accents survive into the resolved final recipe.

Use the capabilities when they serve the brief; do not reduce every edit to a generic trim, but do not force every effect or a generated scene into every video. State why an ordinary cut/no extra effect is appropriate when omitting a treatment. A recommendation is not a new YAML property: there is no document-level `style`, `styles`, `scenePreset`, `transitionFamily` or arbitrary CSS field.

Do not automatically add production labels to titles/captions/watermarks or repeat them in chat. Use subject-relevant copy rather than copying example disclosures. Be honest about generated media; if a disclosure is requested or specifically required, agree on it once rather than putting a banner on every scene. Creative choices do not authorize media access or spending.

The reference is compiled into the same API deployment as the catalog. Installed offline references are snapshots; the live API/schema/compiler wins when versions differ. Never claim that guidance guarantees an LLM's behavior, exact provider cost or rendered visual quality without verification.

Catalog entries are **reference metadata**, not ready-made document objects. Do not paste `label`, `summary`, `category`, `algorithm`, `parameters` definitions, `noRamp`, `defaultDuration`, `xfade` or `xfadeExpr` into YAML clips/effects/transitions. Use the entry's ID at the documented `preset`/`look`/`motion` location and only its supported parameter **values** in `params`. Omit null optional fields. Convert normalized motion frames to actual clip-local keyframe times only if deliberately authoring custom keyframes.
