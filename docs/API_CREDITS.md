# API keys, credits and PayPal Business

Commands and code paths in this guide are relative to the repository root unless stated otherwise.

## Account page

`/api-keys` is a signed-in account page, linked from product navigation, account preferences, `/account` and the API workspace. Keys are still generated by the API, disclosed once and explicitly revocable. PocketBase's `direction_api_keys` rules stay **Superusers only**; `POCKETBASE_URL` and `PB_SERVICE_TOKEN` remain backend-only.

Prepaid Pro access includes 1,000 API credits for each 30-day paid period, anchored to the captured pass's access start. Crossing a calendar-month boundary does not grant another allocation. Advance purchases extend access; their allocation is granted only when that paid period starts. Longer passes receive a new allocation every 30 days, with the last period ending at pass expiry. Unused included credits expire. Separate external subscriptions retain the legacy 1,000-credit UTC calendar-month allocation. Purchased credits do not expire. All application keys belonging to one user share one wallet; included credits are spent first. An expired plan cannot use keys or receive a new allocation.

`balance.allowancePeriod` is `prepaid-30-day` or `calendar-month`; `nextReset` is the exact end of the current included-credit period. The existing `monthlyAllowance` and `monthlyRemaining` names remain for API compatibility and represent included credits for either period type. Existing active prepaid accounts adopt the new period without replenishing an already-granted calendar balance. Settled debits and purchased balances are not rewritten.

## Membership and payment history

`/membership` is the signed-in billing page. Configure `MEMBERSHIP_PLANS_JSON` as an array of `{ "id", "name", "days", "credits", "usd" }` objects: a unique ID (up to 60 bytes), a display name (up to 80 bytes), 1–366 days, 0–1,000,000 bonus credits and a positive USD price with two decimal places. No commercial prices are supplied by the application.

These are **prepaid passes**, not PayPal recurring subscriptions: each checkout is one explicitly approved payment, with no automatic renewal. All plans grant the same existing paid-feature access and the 1,000-credit prepaid-period allocation; `credits` is an additional non-expiring purchased-credit grant, not the included allowance. For the approved $10/30-day pass, set `credits: 0`; setting it to 1,000 would add an unintended second 1,000-credit grant. Passes stack from the later of capture time or existing prepaid expiry. External PocketBase subscriptions remain a separate source of access. No external PocketBase schema changes are needed for prepaid passes.

Membership checkout is available to signed-in free accounts. As with credit packs, only a completed server-verified capture matching the saved owner, reference, currency and price grants access. Browser return parameters never grant access themselves. Authenticated browser features, API-key access and queued-job execution all check the durable local entitlement as well as the existing external subscription contract. Explicit expired/revoked subscription records cannot be rescued by a stale `plan: pro` label.

`GET /billing/orders` returns up to 50 recent account-owned checkouts without capture IDs, owner IDs or internal references. `POST /billing/paypal/orders/<id>/refund-request` saves an owned completed order's reason (10–1,000 Unicode characters, within the 4 KiB request body limit) idempotently. A request is **not an approved refund** and does not issue a payout or change credits. The merchant reviews requests and performs approved refunds in PayPal Business. Verified refund/reversal webhooks remove the applicable credits (or record debt for spent credits) and revoke that order's prepaid access; even a partial refund revokes the refunded pass. Access contributed by other non-refunded passes is recalculated without the refunded days.

To review pending requests privately, stop the API before opening its exclusively locked ledger:

```powershell
docker compose -f compose.editengine.yaml stop api
docker compose -f compose.editengine.yaml run --rm --no-deps api credit-ledger -refund-requests
docker compose -f compose.editengine.yaml start api
```

The command prints private account/order/reason details for the merchant; keep its output out of public logs. It never calls PayPal or issues refunds. There is no customer-accessible refund-approval endpoint or automatic merchant notification. Schedule merchant reviews operationally; sandbox capture/refund/webhook testing remains required before accepting money.

Additional authenticated routes are `GET /billing/access` (authoritative paid-access verdict) and `POST /billing/membership/orders` (`{ "planId": "configured-id" }`). They are not MCP purchase tools and do not authorize an agent to buy access.

## Durable storage

Balances, payment snapshots, capture deduplication, reversals and operation usage records live in `/data/credits.db` (bbolt), outside expiring media sessions. The existing `composition-data` Compose volume persists this file. Billing storage itself needs no PocketBase collection; the asynchronous execution queue separately requires the locked `direction_jobs` migration and hooks described in [BACKGROUND_JOBS.md](BACKGROUND_JOBS.md).

Run **one API instance with one persistent data volume**. The database is exclusively locked, not a distributed billing service. Do not scale API replicas onto independent volumes: that would create independent wallets. Back up the volume; deleting it destroys credit and payment history. A shared transactional database is required before horizontal scaling.

## Configure rates explicitly

Merge `api/.env.billing.example` into the backend environment. These are required business choices, not shipping defaults:

- `CREDIT_USD_VALUE`: positive decimal USD face value represented by one credit. AI debits apply the backend's internal AI tariff before rounding down to whole credits; this value is not a direct exchange rate for external AI spending. Do not expose supplier prices or internal cost-conversion rules in customer interfaces.
- `CREDIT_LEGACY_USD_VALUE`: the **previous** deployed face value when migrating older pending operations that have no saved tariff. The first restart snapshots this value together with the former 30% policy on those operations only. New provider operations snapshot their current face value and 20% policy before the call; later reconciliation uses that snapshot, not newly configured rates. Keep this migration value until all legacy pending operations have been reconciled.
- `CREDIT_RENDER_PER_MINUTE`: positive decimal credit charge per output minute, prorated by compiled output duration and rounded down to whole credits per render.
- `CREDIT_PACKS_JSON`: array of `{ "id": "your-pack-id", "credits": <positive whole number>, "usd": "your-price-with-two-decimal-places" }`. Set the actual numbers yourself; this schema example is not a price offer. Payments are currently in USD.

No rates means versioned API generation/rendering returns 503, rather than running unmetered or inventing a tariff. Reading balances and managing keys remain available. No configured packs/PayPal webhook means checkout is unavailable. The page states these conditions explicitly; it never fills in pretend balances or prices.

### Approved sandbox catalog

`deploy/railway/billing.sandbox.json` records the operator-approved, non-secret configuration for `viral-server`. It does not supply merchant credentials or enable live payments. Apply it together with this release, not by redeploying an older backend that still grants calendar-month credits to prepaid passes.

| Purchase | Price (USD) | Credits |
| --- | ---: | ---: |
| Pro access for 30 days | $10.00 | 1,000 included for that paid period |
| Extra credits | $5.00 | 500 |
| Extra credits | $10.00 | 1,000 |
| Extra credits | $25.00 | 2,500 |
| Extra credits | $50.00 | 5,000 |
| Extra credits | $100.00 | 10,000 |

Every top-up is $0.01 per credit, with no volume discount. `CREDIT_USD_VALUE=0.01` is the commercial face value. Internally, the 20% AI tariff means $0.002 of provider usage corresponds to one credit before whole-credit rounding; $2 of provider usage corresponds to 1,000 credits. This is **not a strict $2 spending cap**: post-usage settlement, rounding and concurrent/pending work can exceed the nominal conversion budget. Hosted browser AI, API and MCP now debit the same account wallet. The existing server-render tariff remains 10 credits per output minute, with scene export and final encoding charged separately, including hosted editor exports. Manual editing and browser-local export remain free. Do not describe the remaining $8 as net profit: payment fees, rendering, storage, infrastructure and taxes are separate costs.

Customer pages show the catalog, retail pack unit prices, included-credit periods, final checkout total, active-access requirement and sandbox notice. They never expose the internal 20% rule or supplier costs. Public pricing loads `GET /billing/catalog`, which returns only the same public catalog/rates used by checkout, without account balances, merchant credentials or internal AI tariff snapshots.

PayPal sandbox simulates **payments only**. It does not make AI generation, server rendering or infrastructure free. Restrict sandbox testing operationally and use test merchant/buyer accounts; do not assume credits obtained through a simulated payment are backed by collected revenue. Switching to live payments requires separate operator approval and verified live credentials/webhooks.

## PayPal Business setup

1. In PayPal Developer, create a REST application under your Business account. Start with **Sandbox** credentials.
2. Set `PAYPAL_MODE=sandbox`, `PAYPAL_CLIENT_ID`, and `PAYPAL_CLIENT_SECRET` on the **API service**. Do not put these into the frontend or PocketBase service.
3. Set `PUBLIC_APP_URL` to the trusted frontend origin. Sandbox permits localhost HTTP; Live requires HTTPS. This controls checkout return/cancel destinations, not a user-submitted URL.
4. Register an HTTPS webhook for your API origin at `/billing/paypal/webhook`, subscribing to `PAYMENT.CAPTURE.COMPLETED`, `PAYMENT.CAPTURE.REFUNDED`, and `PAYMENT.CAPTURE.REVERSED`. Set its ID as `PAYPAL_WEBHOOK_ID`. Use a public development tunnel when the API runs only on localhost.
5. Configure rates and credit packs, recreate the API container, and test checkout, cancellation, repeat verification, refunds and reversals with sandbox accounts.
6. Only after verifying the live deployment, switch to `PAYPAL_MODE=live` and replace **all** credentials and webhook ID with their Live equivalents.

The client sends only a selected pack ID. The API snapshots the owner, credit count, USD amount and a random reference, creates a PayPal order and returns a validated PayPal approval URL. Returning from PayPal does not grant credits by itself: the signed-in owner must have a completed server-verified capture matching the saved amount, currency and reference. A verified webhook also recovers captures when the browser return is lost. Duplicate callbacks do not grant twice. Verified refund/reversal events remove credits or record debt if the purchased credits were already spent; out-of-order reversals block unverified grants.

Backend endpoints:

- `GET /billing/credits`: account balance, reset date, configured rates and available packs; login token required.
- `GET /billing/catalog`: public, rate-limited membership/pack catalog and sandbox/live mode; no authentication or account data.
- `GET /v1/billing/credits`: the same account-scoped summary using an application API key and the existing active Premium/API checks; exposed as the read-only MCP tool `get_credits`. It accepts no owner identity and is not a checkout endpoint. Balance reads do not submit billed work; normal monthly renewal still happens on access.
- `POST /billing/paypal/orders`: `{ "packId": "configured-pack" }`; login and Pro required.
- `POST /billing/paypal/orders/<id>/capture`: verify/capture only the logged-in owner's order.
- `POST /billing/paypal/webhook`: authenticated through PayPal signature verification, not a user login.

## API usage accounting

### MCP client-authored code and paid server rendering

Through `/mcp`, the current client's AI writes/repairs scene CODE without another server-model generation fee. `compile_scene` saves validated live source; it does not encode a scene video. Server scene frame rendering AND final video encoding are charged at `CREDIT_RENDER_PER_MINUTE`, using measured/configured output duration and existing rounding rules. Images, speech and captions/transcription also remain paid. Render jobs need configured rendering rates, available credit, active API access and explicit spending/source consent. Source compilation/lookup and catalog selection are free. Credit summaries expose `mcpPricing.serverRenderingBilled=true` and the scene/video rate separately from the zero code-authoring fee.

The dispatcher assigns the policy; admission persists it and workers restore it before accounting. Older queued MCP render jobs with the superseded free policy are upgraded to billed server rendering at execution. Headers/recipe fields cannot choose free rendering. Pending server scene-model jobs are rejected before paid stages; resolved scene sources can be reused without regenerating their CODE, but server frame export still costs credits. Scene exports are deduplicated per source within an operation and reported as `sceneRenderCredits`; final encoding remains `renderCredits`. Successfully completed scene work is retained if final encoding fails/refunds or the API restarts. Existing settled debits are never repriced. See [MCP client-authored scenes](MCP.md#scenes-written-by-the-current-client-ai).

Metering applies to costly `/v1/projects/<id>/...` application-key operations and newly submitted hosted browser AI/render jobs: AI edit/compositions, images, speech, subtitles, scenes, compile-and-generate and renders (including AI actions staged inside render recipes). Trusted route handlers set `Billed=true`; browser request fields cannot opt out. Workers recheck paid access and balance before provider execution, then settle the same durable owner wallet. Pre-existing browser jobs admitted with `Billed=false` retain their accepted contract; they are not retroactively converted to paid jobs. Standalone local/native CLI execution remains independent of hosted credits. Uploads, validation, ordinary compilation, downloads and polling do not consume credits.

AI calls use the server's existing integration. The API reads verified usage or queries generation metadata for a returned generation ID (including binary-audio generation headers). It does not estimate a fake token tariff. Exact rational arithmetic applies the internal AI pricing policy and rounds each debit down to whole credits before storing it in the existing integer-microcredit ledger. Customer summaries expose credits and public rates, not raw supplier costs or the internal policy. Rendering rates remain independent and unchanged, with the same rounding rule: 2.000015 or 2.4 credits becomes 2, exactly 3 stays 3, and usage below 1 credit becomes 0. Existing balances and previously recorded debits are not rewritten. Actual billed AI work remains charged if a later compilation, cancellation or render fails. Failed final renders release their rendering debit.

All metered application-key operations defer provider metadata lookups until their actions have finished. Generation endpoints save their images/audio and finish compilation before reconciliation; render jobs produce their output first. Successful provider audio is retained when cost metadata is delayed; missing metadata does not turn successful media generation into an error. Multiple provider actions can remain pending within an operation. Completed render responses include `cost.status` (`final` or `pending`), `aiCredits`, `renderCredits`, `knownCredits` and `usdPerCredit`. For `pending`, `knownCredits` is only a subtotal: unresolved usage remains durably recorded for reconciliation, never silently treated as free. Known costs supplied in provider responses are recorded without any additional metadata request; no provider cost is requested before generation.

Credits are **not reserved for current work**. Starting a job leaves the wallet unchanged; verified actual consumption is debited transactionally when the operation settles, monthly credits first. Independent operations can run against the same account without an account-wide hold. Duplicate starts for the same in-flight operation are rejected, usage events are deduplicated and settlement removes the operation atomically. Actual consumption can exceed the remaining balance; the overage becomes debt and blocks new work after settlement. This is post-usage accounting, not an upstream hard-spend cap.

Long-running operations return HTTP 202. Submission validates configured tariffs; an operation record is opened when the worker executes the job, without reserving funds. Subscription access and the settled balance are checked again at execution. A zero balance or debt can fail an accepted job before a provider is called; pending metadata alone does not. Stable `Idempotency-Key` submission retries return the original job. Interrupted running work is not automatically replayed, and failed status writes retry only persistence, avoiding duplicate whole-job execution.

Known provider usage is persisted immediately. Restarting the API settles interrupted operations whose usage is fully known and removes interrupted rendering debits. Ambiguous provider usage stays recorded but does not freeze the wallet or prevent unrelated jobs. Existing legacy account-wide holds are restored to the wallet once on ledger load, preserving all recorded usage and payment history. The `reserved` response field remains zero for compatibility.

Agent estimates are approximate. With sufficient credit, focus on the edit rather than repeated budget negotiation; below 30 remaining credits, give a brief warning and only supported approximate rendering/scene estimates. Report actual consumed credits at the end, distinguishing a pending subtotal from a final cost.

### Reconcile ambiguous usage

Stop the API before opening its exclusively locked database. In Compose, the maintenance binary uses the same persistent volume:

```powershell
docker compose -f .\compose.editengine.yaml stop api
docker compose -f .\compose.editengine.yaml run --rm --no-deps api credit-ledger -owner POCKETBASE_USER_ID
```

The output contains the oldest pending operation and its attempt IDs, not provider credentials. Verify the actual generation and USD cost in OpenRouter. Then run the maintenance command again with `-attempt`, `-generation`, `-usd`, `-usd-per-credit` (the rate when the operation started), and `-confirm`. Supply zero **only after verifying that no billable generation occurred**. The command settles verified cost once all usage is known. Repeat for further pending operations if necessary, then start the API again. Never delete/reset the credit database to discard pending usage.

Alternatively, with the API stopped, `credit-ledger -owner POCKETBASE_USER_ID -reconcile-provider -usd-per-credit ORIGINAL_RATE` fetches the actual cost for recorded generation IDs using the configured backend provider credentials and settles only verified usage. It does not generate any new media and does not assume missing costs are zero. Saved operation tariffs take precedence over current configuration; legacy records must be migrated with the original `CREDIT_LEGACY_USD_VALUE` before changing the deployed policy, or reconciled under the original binary first. Do not reprice settled debits or alter the ledger directly.

## Verification boundary

Automated tests use local fake PayPal/OpenRouter servers and explicitly synthetic account, price and balance fixtures. They do not charge a card, generate billed AI media, deploy a Railway service, or establish that live merchant credentials/webhooks work. Complete the sandbox deployment checks above before enabling real purchases.
